# ReviewTrail network inventory

This inventory covers the installed `reviewtrail` source launcher, its browser reader and the two agent integrations. The last two tables identify calls made by separate upstream tools, build tools or the host application. Selection IDs refer to purposes. Two calls to GitHub can have entirely different purposes.

**Selected to keep:** GitHub review traffic (K1–K3) and the configured LLM provider (K4). The other choices are pending. This checkout has no corporate egress allowlist. The source launcher disables the upstream self-installer to avoid overwriting a separate Plannotator install.

## Traffic that supports a review

| ID | Trigger and destination | What crosses the boundary |
|---|---|---|
| L0 | Open the local reader. Browser ↔ local ReviewTrail server on a random port. | Diff, guide passages, drafts, comments, settings and job status. Returning comments to the calling agent is a local handoff. The agent may include them in its next provider request. |
| K1 | Open, refresh or switch a GitHub PR, inspect references or browse files. GitHub REST/GraphQL through `gh`, including the configured GitHub Enterprise host. | Authenticated queries containing repository, PR/issue number, refs, paths or logins. Responses include source, discussion, checks and metadata. A PR can refresh while open. |
| K2 | Select a GitHub action such as submitting a review or replying to a thread. Same GitHub host. | Review text, chosen approval/change request, line or file anchors, and relevant PR/commit/thread IDs. Drafting an inline comment locally does not publish it. |
| K3 | Prepare a checkout for a GitHub PR (default), or explicitly fetch a GitHub remote. Git over HTTPS or SSH to the repository or fork. | Repository identity, negotiated refs and object IDs, credentials through Git's configured mechanism, and downloaded source. `--no-local` skips the checkout for a PR. |
| K4 | Generate a guide, ask a question, start another AI review or query a provider’s models. The chosen agent CLI/SDK, its configured LLM gateway and applicable auth endpoints. | Prompts, code/diff, question, relevant repository/tool context and model selection, depending on the action. Auth and discovery differ by provider. An ordinary local diff can be read without generating a guide. |

Implementation: [review API](packages/server/review.ts), [GitHub operations](packages/shared/pr-github.ts), [CLI checkout](apps/hook/server/index.ts), [guide generation](packages/server/guide/guide-review.ts), [AI providers](packages/ai/providers), [Pi handoff](integrations/pi/index.ts).

## Traffic controlled outside ReviewTrail

| ID | Owner and trigger | Destinations and data |
|---|---|---|
| H1 | Install/build/update tooling | Bun/npm resolve dependencies and fetch package names, versions and tarballs from the registry or configured mirror. Git dependencies and host/tool downloads can contact GitHub or the configured tool vendor. The ReviewTrail symlink installer operates locally after dependencies and UI are built. CI and deployment jobs have their own service traffic. [Lockfile](bun.lock), [installer](scripts/install-reviewtrail.ts) |
| H2 | Claude Code Desktop, Claude Code CLI, account and configured extensions | Inference and auth, plus potential host-managed updates, diagnostics, feature/config sync, connectors/MCP and remote sessions. | H3 | Pi agent 0.84.4 | Startup can check `pi.dev/api/latest-version`, report install version to `pi.dev/api/report-install`, check installed packages, or download missing tool binaries such as ripgrep from GitHub Releases. Pi documents `--offline` / `PI_OFFLINE=1` for startup networking and `PI_TELEMETRY=0` for install telemetry. Model calls, user-invoked tools, extensions and explicit package commands have their own network behavior. Verified against the installed Pi CLI and its version-check and interactive-mode code. |
| H4 | Browser, OS, Git, credential helpers and agent tools | An external link targets the URL the reviewer opens. Credentials may use SSO/token refresh, Git can use SSH proxies, LFS or custom remote helpers, installed forge CLIs can check for their own updates, and agents may use a configured web tool or MCP service. ## Verification and selection

A production-browser run opened the 58-file, 2,388-line patch, generated a guide through a local stand-in for Claude, expanded code, navigated between behaviors, saved progress, switched to the diff and opened a line comment. The browser attempted **zero external HTTP(S) origins** across **46 distinct loopback paths**. The run used a static patch and local provider. Authenticated GitHub, live provider sessions, exported guides, cold installs, release builds and the Desktop process were outside that capture. The other rows come from inspection of source paths, subprocess commands and browser asset loaders. Configurable origins and user-provided URLs make this a call-type inventory, not an exhaustive list of possible DNS names.

Select IDs individually, for example, “remove N1–N4 and N12, make N5 manual, and allow GitHub attachments only for N9.” No removal choices have been inferred for the remaining rows.
